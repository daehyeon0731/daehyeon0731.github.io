블로그 구축 — 툰엔진 연구 기록을 남길 공간

툰엔진을 새로 만들기 전에, 매 커밋의 의사결정을 기록할 블로그부터 세웠다.

Commits

  • 1단계 — Astro 프로젝트 초기화, 레이아웃과 디자인 토큰

툰엔진을 처음부터 다시 만들기로 했다. 그 과정의 모든 결정과 이유를 커밋 단위로 남기기 위해, 먼저 기록할 공간을 만든다.

커밋 1 — 블로그 구축

하루 작업을 한 커밋으로 묶었다. 작업은 아래 다섯 단계로 진행했다.

1단계 — Astro 프로젝트 초기화, 레이아웃과 디자인 토큰

결정 Jekyll(GitHub Pages 기본) 대신 Astro로 정적 사이트를 구성하고, 기성 테마 없이 처음부터 디자인한다.

이유

  • 메인 화면에 WebGL 셰이더를 직접 올릴 계획이다. Astro는 기본적으로 JS를 내보내지 않고 필요한 컴포넌트에만 스크립트를 붙일 수 있어서, 글 페이지는 가볍게 유지하면서 셰이더 페이지만 무겁게 만들 수 있다.
  • 콘텐츠 컬렉션에 스키마(zod)를 걸 수 있어서 Works / Blog / Devlog 를 타입이 있는 데이터로 관리할 수 있다.
  • 이미 설치된 Node 만으로 로컬 미리보기가 된다. Jekyll 은 Ruby 설치가 추가로 필요하다.
  • 테마(Chirpy, AstroPaper 등)는 문서형 디자인이 강해서 NPR / 수채화 콘셉트를 입히려면 결국 대부분을 뜯어고쳐야 한다.

구성

  • 종이색 배경 + 잉크색 텍스트, 수채화 안료 4색(인디고·로즈·오커·새프그린)을 CSS 토큰으로 정의
  • 라이트 / 다크 테마: 시스템 설정을 따르되 토글로 강제 가능 (data-theme)
  • 페이지 전체에 SVG feTurbulence 로 만든 종이 그레인 오버레이
  • 공용 SVG 필터 wc-bleed: 노이즈 디스플레이스먼트 + 침식(erode)으로 테두리를 분리해 수채화 얼룩을 흉내

대안

  • Hugo: 빌드는 가장 빠르지만 Go 템플릿으로 인터랙티브 컴포넌트를 다루기 불편하다.
  • Next.js: 블로그 용도로는 과하다. 정적 페이지가 기본인 Astro 가 목적에 더 맞다.

2단계 — 실시간 수채화 셰이더 히어로

결정 메인 화면 배경을 이미지가 아니라 단일 패스 WebGL 프래그먼트 셰이더로 그린다. Three.js 없이 순수 WebGL 로 작성한다.

이유

  • 내가 하는 일이 NPR 이다. 첫 화면 자체가 작업물이자 자기소개가 되도록 했다.
  • 상태를 저장하지 않는 단일 패스로 만들면 FBO 핑퐁 없이 어떤 해상도에서도 바로 재현되고, 코드가 짧아 설명하기 쉽다.
  • 풀스크린 삼각형 하나만 그리면 되므로 Three.js(약 600KB)는 과하다.

구현한 수채화 현상

현상 근사 방법
번짐 형태 도메인 워핑 fBm (q → r → d 2단 워프)
엣지 다크닝 임계값 바로 위의 얇은 띠를 따로 계산해 진하게 더함
안료 불균일 저주파 노이즈(flow)로 내부 농도를 흔듦
그래뉼레이션 종이 높이 노이즈로 안료 농도를 변조
글레이징 레이어를 투과색으로 보고 곱함 (감산 혼합)
종이 콜드프레스 결 + 섬유 + 높이 그라디언트로 엠보스
젖은 붓 포인터 궤적 32점을 유니폼으로 넘겨 번짐 + 테두리

튜닝 기록 첫 버전은 워프 강도(3.0 / 2.4)와 그레인 주파수(px/3.5)가 높아서 종이가 찢어진 것처럼 보였다. 워프를 1.8 / 1.6 으로, 그레인을 px/7 로, 그래뉼레이션 폭을 0.7–1.3 에서 0.82–1.18 로 낮췄다. 내부는 연하고 가장자리만 진한 수채화다운 형태가 나왔다.

성능과 접근성

  • DPR 상한 1.5, 화면 밖(IntersectionObserver)이거나 탭이 숨겨지면 렌더링 중단
  • prefers-reduced-motion 이면 애니메이션 없이 정지된 그림 한 장만 그림
  • WebGL 을 쓸 수 없으면 CSS radial-gradient 로 대체

대안

  • 이전 프레임을 누적하는 wet-in-wet 시뮬레이션: 더 사실적이지만 상태 관리가 필요하다. 다음 단계 연구 주제로 남긴다.

3단계 — 포트폴리오 · 블로그 콘텐츠 구조

결정 Works(포트폴리오)와 Blog(연구 노트)를 별도 컬렉션으로 나누고, 둘 다 마크다운 파일 하나가 글 하나가 되도록 한다.

이유

  • Works 는 결과물(영상, 브레이크다운) 중심이고 Blog 는 과정과 원리 중심이다. 보여주는 방식이 다르니 스키마도 나눴다. Works 에는 tools, cover, featured 가 있다.
  • 커버 이미지가 없는 작업도 카드가 비어 보이지 않도록, 작업 id 를 시드로 쓰는 수채화 얼룩 SVG 를 자동으로 그린다.
  • 글 본문의 코드 블록은 1단계에서 설정한 Shiki 듀얼 테마(rose-pine-dawn / rose-pine-moon)를 따라 사이트 테마와 함께 바뀐다.
  • 블로그 목록은 태그 필터를 클라이언트에서 처리한다. 글 수가 적을 때는 서버 라우팅보다 단순하다.

정리 구조를 잡으려고 넣었던 예시 작업 2개(툰 셰이더, 잉크 라인)는 실제 작업이 아니라서 뺐다. Works 에는 실제로 만든 것만 올린다.

4단계 — Devlog 섹션

결정 작업 일지를 블로그 글과 분리된 Devlog 섹션으로 두고, 하루에 파일 하나, 커밋마다 섹션 하나로 기록한다. 각 섹션은 결정 / 이유 / 대안 형식으로 쓴다.

이유

  • 블로그 글은 완성된 설명이고, Devlog 는 진행 중인 판단의 기록이다. 섞으면 둘 다 읽기 어려워진다.
  • 커밋 메시지는 무엇을 바꿨는지만 담기에도 짧다. 왜 그렇게 했는지, 무엇을 버렸는지는 따로 남겨야 나중에 다시 판단할 때 근거가 된다.
  • 기록을 해당 커밋과 같은 커밋에 넣는다. 그러면 git 기록에서 코드 변경과 그 이유가 항상 함께 움직인다.
  • 상세 페이지는 ## 커밋 제목을 읽어 목차를 자동으로 만들고, 목록에는 하루 커밋 수를 표시한다.

대안

  • GitHub 커밋 메시지 본문에만 쓰는 방법: 따로 관리할 것이 없지만 사이트에서 읽기 어렵고 표나 코드를 넣기 불편하다.
  • 커밋 하나에 글 하나: 하루 작업의 흐름이 잘게 쪼개져서 맥락이 끊긴다.

5단계 — GitHub Actions 배포, 줄바꿈 통일

결정 main 에 push 하면 GitHub Actions 가 빌드해서 GitHub Pages 로 배포한다. 저장소의 줄바꿈은 LF 로 통일한다.

이유

  • 빌드 결과물(dist/)을 저장소에 올리지 않아도 된다. 기록에는 소스와 결정만 남는다.
  • 공식 withastro/action 이 패키지 매니저 감지, 캐시, Pages 아티팩트 업로드까지 처리한다.
  • Windows 에서 작업하고 Linux 러너에서 빌드하므로, .gitattributes 로 LF 를 고정해 줄바꿈 차이로 생기는 불필요한 diff 를 막는다.

대안

  • gh-pages 브랜치에 빌드 결과를 커밋: 설정은 익숙하지만 결과물 커밋이 기록을 어지럽힌다.

커밋 2 — 소스 비공개, 결과물만 공개 배포

결정 블로그 소스를 비공개 저장소로 옮기고, 빌드한 결과물만 공개 저장소 daehyeon0731.github.io 의 gh-pages 브랜치로 배포한다.

이유

  • 개인 블로그다. 글과 사이트는 공개하되, 사이트를 만드는 원본 코드와 작업 기록까지 공개할 이유는 없다.
  • GitHub Pages 의 사용자 사이트 주소(github.io)를 그대로 쓰면서 무료 플랜에서 할 수 있는 방법이다.
  • 배포 인증은 공개 저장소 하나에만 쓰기 권한이 있는 Deploy key 로 한다. 계정 전체 권한이 걸리는 개인 토큰보다 유출됐을 때 피해 범위가 작다.
  • force_orphan 으로 배포할 때마다 커밋 하나로 덮어쓴다. 공개 쪽에는 배포 기록이 쌓이지 않는다.

한계 브라우저에서 실행되는 코드(수채화 셰이더 등)는 방문자가 내려받아야 실행되므로, 압축은 되어도 완전히 숨길 수는 없다. 숨겨지는 것은 원본 소스와 기록이다.

대안

  • GitHub Pro 로 비공개 저장소에서 바로 Pages: 저장소 하나로 끝나지만 유료이고, 플랜이 끝나면 사이트도 멈춘다.
  • Cloudflare Pages / Netlify: 비공개 저장소를 바로 연결할 수 있지만 github.io 주소를 쓸 수 없다.
